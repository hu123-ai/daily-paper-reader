## 摘要
我们提出了鲁棒智能体补偿（Robust Agent Compensation, RAC），这是一种基于日志的恢复范式（提供安全网），通过架构扩展实现，可应用于大多数智能体（Agent）框架，以支持可靠执行（避免意外副作用）。用户可以选择启用 RAC，而无需更改其当前的智能体代码（例如 LangGraph 智能体）。所提出的方法可以通过现有扩展点在大多数现有智能体框架中实现。我们展示了一个基于 LangChain 的实现，通过 τ-bench 和 REALM-Bench 证明了其可行性，并表明在解决复杂问题时，与最先进的基于大语言模型（LLM）的恢复方法相比，RAC 在延迟和 Token 经济性方面均优于 1.5-8 倍或更多。

## Abstract
We present Robust Agent Compensation (RAC), a log-based recovery paradigm (providing a safety net) implemented through an architectural extension that can be applied to most Agent frameworks to support reliable executions (avoiding unintended side effects). Users can choose to enable RAC without changing their current agent code (e.g., LangGraph agents). The proposed approach can be implemented in most existing agent frameworks via their existing extension points. We present an implementation based on LangChain, demonstrate its viability through the $τ$-bench and REALM-Bench, and show that when solving complex problems, RAC is 1.5-8X or more better in both latency and token economy compared to state-of-the-art LLM-based recovery approaches.

### 2. 论文提出的方法论
*   **核心思想**：将恢复逻辑与智能体的推理逻辑解耦。通过拦截器记录所有工具调用，并在失败时执行确定性的补偿逻辑。
*   **关键技术细节**：
    *   **架构组件**：包括工具拦截器（Tool Interceptor）、错误拦截器（Error Interceptor）、事务日志（Transaction Log）和恢复与补偿管理器（RCManager）。
    *   **算法流程**：
        1.  **记录**：拦截器将每个工具调用的开始、完成和错误状态记录在持久化日志中。
        2.  **故障处理**：当检测到错误时，RCManager 首先尝试**重试**（针对瞬时错误），若失败则尝试**寻找替代方案**（利用 LLM）。
        3.  **回滚（Rollback）**：若上述均失败，则根据日志构建执行图，按 **LIFO（后进先出）** 顺序执行补偿操作（如“取消航班”对应“预订航班”）。
    *   **补偿对发现机制**：RAC 按优先级通过三种方式获取补偿操作：(1) 框架 API 配置；(2) **模型上下文协议（MCP）** 注释；(3) LLM 自动推断。

### 6. 论文的主要结论与发现
*   **性能卓越**：在处理复杂问题时，RAC 的 **Token 经济性提升了 1.5-8 倍**，延迟显著降低。
*   **鲁棒性强**：在面对“动态故障”时，原生 ReAct 和 SagaLLM 经常陷入昂贵的重新规划循环或直接失败，而 RAC 能通过确定性的回滚逻辑稳定处理。
*   **解耦优势**：将恢复逻辑从 LLM 推理中剥离，不仅降低了幻觉风险，还简化了智能体的推理负担，使其能解决更难的问题。
*   **标准化**：通过扩展 MCP 协议，为工具开发者提供了一种标准化的方式来定义补偿操作。

### 7. 优点
*   **非侵入性**：无需修改现有智能体代码即可启用，易于集成到 LangGraph、CrewAI 等主流框架。
*   **确定性恢复**：相比于让 LLM “思考”如何修复错误，基于日志的回滚更加可靠且可预测。
*   **互操作性**：利用 MCP 协议，使得不同厂商开发的工具能够自带“撤销”属性。

### 8. 不足与局限
*   **简化假设**：RAC 假设没有定义补偿操作的工具就没有副作用（如 `print`），但在某些复杂场景下，这可能导致漏掉必要的清理工作。
*   **回滚策略单一**：目前主要采用全量回滚（Rollback everything），对于只需要局部修复的超大规模工作流，可能存在过度补偿的问题。
*   **依赖工具设计**：RAC 的效能高度依赖于工具库是否提供了对应的补偿工具（如取消接口）。如果缺乏补偿手段，RAC 也无法凭空撤销物理世界的副作用。
