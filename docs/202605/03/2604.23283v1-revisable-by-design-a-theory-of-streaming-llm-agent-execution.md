## 摘要
目前的 LLM 智能体在一个隐含但普遍的假设下运行：执行是一个事务——用户提交请求，智能体独立工作，只有在完成后对话才会恢复。这迫使用户面临二选一的境地：要么等待可能错误的结果，要么中断并丢失所有进度。我们拒绝这一假设，并提出了流式范式（stream paradigm），其中智能体执行和用户干预是共享双向通道的并发、交织过程。我们通过一种可逆性分类法（reversibility taxonomy）将该范式形式化，该分类法将每个智能体动作归类为幂等（Idempotent）、可逆（Reversible）、可补偿（Compensable）或不可逆（Irreversible），并得出一个核心结论：智能体的灵活性受其可逆性的限制。我们证明了冲突的可补偿动作会带来不可避免的适应成本，而冲突的不可逆动作则使得完全满足规范变得不可能——这些成本是动作空间的属性，而非算法的属性。基于这一见解，我们提出了 Revision Absorber，这是一种基于“最早冲突回滚”（Earliest-Conflict Rollback）规则的反应式算法，在温和的假设下具有结构最优性。在 StreamBench 上对真实 LLM 智能体进行的实验验证了所有预测：Absorber 的质量与暴力全重启基线相当，但浪费的已完成工作步骤减少了一个数量级，将执行过程中的修订从死胡同转变为一种一等公民式的交互。

## Abstract
Current LLM agents operate under an implicit but universal assumption: execution is a transaction -- the user submits a request, the agent works in isolation, and only upon completion does the dialogue resume. This forces users into a binary choice: wait for a potentially incorrect output, or interrupt and lose all progress. We reject this assumption and propose the stream paradigm, in which agent execution and user intervention are concurrent, interleaved processes sharing a bidirectional channel. We formalize this paradigm through a reversibility taxonomy that classifies every agent action as Idempotent, Reversible, Compensable, or Irreversible, and arrive at a core conclusion: an agent's flexibility is bounded by its reversibility. We prove that conflicting compensable actions impose unavoidable adaptation costs and that conflicting irreversible actions make full specification satisfaction impossible -- these costs are properties of the action space, not of the algorithm. Guided by this insight, we present the Revision Absorber, a reactive algorithm based on the Earliest-Conflict Rollback rule that is structurally optimal under mild assumptions. Experiments on StreamBench with real LLM agents validate all predictions: the Absorber matches the quality of a brute-force full-restart baseline while wasting an order of magnitude fewer steps of already-completed work, turning mid-execution revisions from a dead-end into a first-class interaction.

### 论文总结：设计即时可修订——流式 LLM 智能体执行理论

#### 1. 核心问题与整体含义
*   **研究动机**：当前的 LLM 智能体（Agent）大多遵循“事务性假设”（Transactional Assumption），即用户提交任务后，智能体进入闭环执行，用户只能在任务结束或失败后重新介入。这种模式在长程任务中存在弊端：如果用户中途发现方向偏差或需求变更，只能选择“等待错误结果”或“中断并丢失所有进度”。
*   **核心问题**：如何打破这种二元选择，实现用户在智能体执行过程中的实时干预与修正，且不造成不必要的资源浪费？

#### 2. 方法论
*   **核心思想**：提出“流式范式”（Stream Paradigm），将智能体执行与用户干预视为共享双向通道的并发过程。
*   **关键技术细节**：
    *   **状态分解**：将智能体状态分为“认知状态”（Epistemic，可随时回滚的上下文）和“世界状态”（World，部分可回滚的外部环境影响）。
    *   **可逆性分类学（{I, R, K, X}）**：
        *   **I (Idempotent)**：幂等动作，不改变世界状态（如读取文件）。
        *   **R (Reversible)**：可逆动作，有精确的逆操作（如创建/删除文件）。
        *   **K (Compensable)**：可补偿动作，无精确逆操作但可补救（如发送更正邮件）。
        *   **X (Irreversible)**：不可逆动作，无法补救（如完成金融转账）。
    *   **核心理论**：证明了智能体的灵活性边界由其动作空间的可逆性决定。
*   **算法流程（Revision Absorber）**：
    1.  **扫描冲突**：当用户注入修正（Injection）时，扫描执行轨迹，寻找最早的与新规范冲突的 K 或 X 类动作。
    2.  **回滚与补偿**：将认知状态回滚至冲突点前；对冲突点后的 R 类动作执行逆操作，对 K 类动作执行补偿操作。
    3.  **重新规划**：在更新后的上下文和世界状态基础上，让智能体重新生成后续计划。

#### 3. 实验设计
*   **数据集/场景**：构建了 **StreamBench** 基准测试，包含三个多步工具调用场景：活动策划（Event Planning）、旅行安排（Travel Arrangement）、报告与发布（Report & Publish）。
*   **Benchmark 设置**：通过调整工具集中 K/X 类工具的比例，设定了四个不同的可逆性比例（ρ ∈ {1.0, 0.75, 0.5, 0.25}）。
*   **对比方法**：
    *   **Oracle**：上帝视角，任务开始前就已知修正。
    *   **Full-Restart**：暴力全重启，补偿所有动作并从头开始。
    *   **Naive Absorber**：仅将修正追加到上下文，不进行回滚。
    *   **Ignore**：完全忽略用户修正。
    *   **其他**：包括 Checkpoint-K 和 LangGraph-Interrupt 等系统启发式模式。

#### 6. 主要结论与发现
*   **性能表现**：Revision Absorber 在输出质量上与“全重启”基线统计学无显著差异，但在“浪费步骤”这一指标上比全重启**减少了 14.6 倍**。
*   **理论验证**：实验证实了“灵活性受限于可逆性”的理论，即任务的可逆性比例（ρ）越低，任何算法都无法避免更高的补偿成本。
*   **模型无关性**：浪费步骤的减少是算法结构的属性，在不同能力的 LLM（DeepSeek, Claude, GPT）上表现一致；而最终质量则取决于 LLM 的重新规划能力。

#### 7. 优点
*   **范式突破**：将智能体交互从“事务性”转变为“流式”，更符合人类真实协作场景。
*   **理论严谨**：引入分布式数据库中的补偿语义，为智能体动作空间建立了形式化的分类学。
*   **高效实用**：算法复杂度低（O(m)），无需复杂的搜索或代价估算，易于集成到现有智能体框架中。

#### 8. 不足与局限
*   **工具模拟风险**：实验主要在模拟工具环境下进行，真实世界 API 的可逆性标注（如识别某个 API 是否可补偿）可能需要额外的人工或模型标注成本。
*   **模型能力依赖**：该方法依赖于智能体的“重新规划”能力，在较弱的模型上，回滚后的表现提升有限。
*   **假设限制**：算法假设 I/R 类动作不会对未来计划产生逻辑约束，但在某些极端的强逻辑依赖任务中，这可能导致信息丢失。
